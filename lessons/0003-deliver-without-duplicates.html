Lesson 0003 · 10 minutes

Deliver without duplicates

Your tangible win: route a worker-completion callback across active-turn races and ambiguous network failures without losing it or blindly sending it twice.

Starting point. You already know that Impala needs both the correct app-server endpoint and the originating threadId. Now we make delivery reliable.

The dangerous failure is “unknown”

Suppose Impala sends turn/start, then its socket closes before the response arrives. Two histories fit the evidence:

  • The server never accepted the request; retrying is necessary.
  • The server accepted it; retrying may create a duplicate turn.

A timeout is therefore not failure. It is unknown outcome. The correct next operation is reconciliation.

Persist before sending

When the worker reaches a terminal state, Impala first inserts one durable outbox record keyed by the delegation and worker completion. Repeated hooks find the existing record instead of creating another callback.

Route by the source thread’s state

Idle thread

Call turn/start. This callback is a new unit of work.

Active thread

Use thread/queue/add when the negotiated experimental capability is available.

No queue capability

Leave the outbox record pending and send after turn/completed.

turn/steer is wrong for normal worker completion. Steering changes the meaning of work already running; completion should become a distinct later turn.

The current protocol requires a unique clientUserMessageId for queued input and carries it into the queued submission. User-message items also expose the supplied client ID, making it useful for correlation after reconnect.

Correlation is not automatically idempotency. The public protocol reference does not promise that submitting the same client message ID twice becomes one turn. Impala must search queue and thread state for that ID before retrying.

Reconcile after uncertainty

  1. Reconnect and initialize against the same daemon.
  2. Resume the originating thread.
  3. List queued submissions and inspect returned user-message history for the client message ID.
  4. If present, mark the outbox record accepted; do not resend.
  5. If absent, route once according to current thread state and persist the returned turn or queue ID.

thread/queue/add, list, and delete are currently experimental and require capabilities.experimentalApi. A production Impala integration needs the pending-until-idle fallback rather than making queue support mandatory.

Retrieval check

1. The source thread is active and queue capability is available.

2. The socket closes after sending but before the response.

3. Impala receives the same worker-completion hook twice.

The resulting Impala contract

  1. Worker completion creates or finds one durable outbox record.
  2. Delivery always targets the recorded server and thread identities.
  3. Active threads queue or wait; they are not steered.
  4. Network uncertainty triggers reconciliation.
  5. Acknowledged turn or queue IDs close the retry window.
