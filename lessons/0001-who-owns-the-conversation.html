The app server owns the conversation

Your tangible win: place the TUI, Impala, and app server on the correct side of the boundary, then route an agent-completion message safely.

Core model. The TUI is a client, not the conversation. A thread can survive a client disconnect because the app server owns its state and execution.

One server, multiple clients

Codex exposes a JSON-RPC protocol. A client connects, sends initialize as its first request, then creates or resumes threads and receives streaming notifications. The same semantics can travel over stdio, WebSocket, or the daemon’s Unix control socket.

Codex TUIRenders items, accepts keyboard input, shows approvals and process state.
↔
Codex app serverOwns thread history, active turns, tools, approvals, persistence, and notifications.
↔
ImpalaRecords thread identity, observes delegated work, and submits completion input.

The model provider and local tool processes sit behind the app server; clients do not coordinate them through terminal keystrokes.

This changes the Impala design. The PTY may still display and control the TUI, but PTY text injection should not wake a thread. Impala should connect as another protocol client and address the originating threadId.

Thread, turn, item

Thread

The durable conversation. It contains ordered turns and can be resumed by ID.

Turn

One user submission plus the generation and tool work it triggers.

Item

A typed unit inside a turn: messages, commands, file changes, plans, and more.

While a turn runs, the server emits turn/started, ordered item/* events, and finally turn/completed. The UI renders these events; it does not infer authoritative completion from whether a terminal looks quiet.

Route completion input by thread state

turn/start

Use when the thread is idle. It creates a new user turn and starts generation.

turn/steer

Use to amend the current active turn. It requires the expected active turn ID.

thread/queue/add

Use to preserve a later user turn while another runs. This API is experimental.

For Impala’s agent completion, the normal path is turn/start after the orchestrator is idle. If completion races with an active turn, queueing expresses “run this next” more accurately than steering, but Impala must capability-check and isolate that experimental API.

Retrieval check

Choose from the same three operations. Each answer has four words; formatting gives no hint.

1. The worker finished and the orchestrator thread is idle.

2. The worker finished while the orchestrator is still handling another user request.

3. The user says “focus on the failing test first” during the current turn.

Apply it to Impala

  1. Launch or connect the TUI to the managed app server.
  2. Capture the orchestrator’s threadId when delegation begins.
  3. Let Impala observe the worker’s authoritative lifecycle event.
  4. Submit a deduplicated completion message to the originating thread.
  5. Render the resulting turn through the already-connected TUI.
