Codex app-server field guide

The smallest useful map for reviewing Impala’s structured Codex integration.

Ownership

App server

Owns threads, turns, items, tool execution, approvals, persistence, and event production.

Client

Sends JSON-RPC requests, subscribes to notifications, renders state, and answers approvals.

Transport

Carries protocol messages over stdio, WebSocket, or the managed Unix control socket.

Lifecycle

  1. Connect to the transport.
  2. Send initialize first; then signal initialized.
  3. Create or resume a thread.
  4. Start, steer, or queue user input.
  5. Consume turn/started, item/*, and turn/completed.

Input routing

turn/start

The thread is idle. Create a new turn and trigger generation.

turn/steer

The thread is active. Amend that exact active turn using its expected turn ID.

thread/queue/add

The thread is active. Persist input for a later turn. Experimental API.

Impala review checklist

  • Is the originating threadId captured when delegation starts?
  • Does every completion message have a stable client message ID for deduplication?
  • Does delivery distinguish idle from active threads?
  • Can daemon restart and socket loss be retried without duplicating a turn?
  • Does the PTY remain a rendering/input surface rather than the control protocol?
  • Are experimental queue semantics isolated behind a capability check?
